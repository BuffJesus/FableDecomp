## TL;DR verdict

- **Representation is real but it is "2.5-D stacked layers + discrete transition edges," NOT true 3-D.**
  Each `CNavigationLayer` is an independent, full-map quad-tree in the **same (x,y) plane**; layers
  overlap freely in x,y (that is exactly how a bridge sits over ground). A node knows only its
  `navLayer` byte and a 2-D centre — there is no Z in the nav data at all. Walking between layers happens
  **only at explicit transition points**: sparse, reciprocal neighbour links between two leaves that share
  an (x,y) footprint on adjacent layers.
- **A spiral ramp that continuously overlaps itself in x,y is NOT representable as one continuous surface.**
  It must be **cut into discrete horizontal layers** (one per "wrap" of the spiral), each a flat 2-D
  patch, joined at hand-defined transition points. Max is bounded by what the engine builds — the retail
  ceiling is **5 layers** (HookCoast). So a 2–4 turn spiral staircase = plausible; a smooth continuous
  helix = not directly.
- **The layers and transitions are AUTO-GENERATED by the editor at nav-build time — but only from real
  PHYSICS COLLISION geometry plus nav-hint things.** The generator reads (a) the LEV terrain walkable grid,
  (b) each placed thing's **physics collision mesh**, and (c) things that carry *navigation information*
  (`HasNavigationInformation` — buildings/floors, `NAVIGATION_SEED`, `TRANSITION_GATE`). The **layer index
  at a point is decided by `GetNavigationLayerAt`**, which asks the nav-info things overlapping that point
  "what layer am I?". So multi-layer nav is *derived*, but it requires the multi-level geometry to exist as
  collision and requires nav-info hints — it does **not** fall out of a bare graphics mesh.
- **Spiral Mountain today is a graphics-only mesh** (`MESH_FORGE_SPIRAL_MOUNTAIN`, one merged prim in a
  staged `graphics.big`); it has no `[PHYSICS]` collision mesh and no nav-info things. On its own it is
  **decorative and non-walkable** for creatures. The hero can still be pushed onto it only where the flat
  terrain heightfield underneath is walkable.
- **Realistic authoring path: native, single-layer, per-wrap.** Extending the hub's terrain-only generator
  to emit *stacked* layers + transition edges is a **medium job** (format is fully known; the hard part is
  deciding layer membership and transition placement from a mesh — see §4). The editor route only works if
  ego_r/FableWin can ingest your mesh **as physics collision** with per-floor nav-info things, which is the
  same authoring problem in a tool we barely drive.

## 1. How multi-layer nav is REPRESENTED and TRAVERSED (decompiled + corpus-proven)

### 1.1 On disk: stacked same-plane quad-trees tagged by `navLayer`

From `NAVMESH_RE.md` (proven, byte-exact): a `CNavQuadTree` block carries `numLayers`, then a flat list
of node records. Every real node has:

- `detailLevel` (`+0x0c`): quad-tree subdivision level 0..7, size `= 32/2^level` map units.
- **`navLayer`** (`+0x0d`): the vertical layer index (0 = ground, 1.. = upper).
- `posX, posY`: a **2-D** centre (map-relative). **There is no Z stored anywhere in the nav data.**

`LoadFromFile` groups nodes per layer into `vector<CNavigationLayer>` and asserts, for each,
`pnode->GetNavLayer()==current_nav_layer` (`lib_nav_quad_tree.cpp:0x672`). So each layer is its own
complete quad-tree over the **same x,y map box**; "multi-layer" = N quad-trees stacked in the same plane,
distinguished only by the `navLayer` byte. Overlap in x,y between layers is the whole point (bridge over
ground, mezzanine over floor).

### 1.2 Inter-layer connection = transition points → cross-layer neighbour links

The engine builds a per-layer neighbour graph (same-layer edge adjacency), then stitches layers with
**`CNavQuadTree::JoinNavigationLayers` (0x03291790)**. Decompiled this session (full body):

```
JoinNavigationLayers():
  for each CNavigationTransitionPoint tp in this->transitionPoints:   # vector<CNavigationTransitionPoint>
      lower = GetNodeAt(tp.pointA)      # tp+0x08 : resolves the leaf covering that (x,y) ...
      upper = GetNodeAt(tp.pointB)      # tp+0x0c : ... on whichever layer that node lives in
      if lower && upper && lower->IsNavigable() && upper->IsNavigable():
          lower.neighbours.push_back(upper)      # CSmallVector<CANavQuadTreeNode*>
          upper.neighbours.push_back(lower)      # reciprocal
```

So a transition point is a **pair of 2-D points**; each resolves to a leaf (possibly on different layers),
and the two leaves are made **mutual neighbours**. That link is written to disk in the ordinary neighbour
list — there is no separate on-disk transition structure. `VerifyTransitionPoints` (0x03291a20) just
re-resolves every transition point and asserts both ends are navigable (validation only:
`"clower_node && cupper_node && clower_node->IsNavigable() && cupper_node->IsNavigable()"`).

Runtime pathfinding is a single `CNavigatorAStar` over the leaf-neighbour graph
(`CAStarState` 0x031a7110). Because cross-layer links are just neighbours, A* walks between layers with
**zero special-casing** — a transition edge is traversed like any other adjacency. There is no "climb"
primitive; the geometry/animation just carries the creature along the surface the layer represents.

### 1.3 Corpus ground truth (real multi-floor interiors, not just decomp)

Extracted all 399 LEVs from `FinalAlbion.wad`. **46 are multi-layer** (see full table in the session
report). Studied the cross-layer neighbour edges directly:

| Level | layers | leaves/layer | cross-layer edges | pairs |
|---|---|---|---|---|
| **HeroGuildComplexInside** (multi-floor building) | 3 | {0:6807, 1:1425, 2:970} | 32 | (0,1):28, (1,2):4 |
| **BarrowFields** (bridge over ravine) | 2 | {0:2224, 1:110} | 4 | (0,1):4 (= 2 points ×2 dirs) |
| **Bordello** (upper mezzanine) | 2 | {0:1412, 1:195} | 2 | (0,1):1 point |
| **HauntedHouse** | 2 | {0:1911, 1:295} | 2 | (0,1):1 point |
| HookCoast | **5** | {0:4054,1:1258,2:105,3:64,4:39} | — | — |
| PrisonCourtyard | 4 | {0:1331,1:248,2:631,3:1079} | — | — |

Proven facts from the raw bytes:

1. **Cross-layer edges are sparse and reciprocal** — a handful of transition *points*, each contributing
   one bidirectional link. Layer 1 is typically a small **patch** over the map (BarrowFields' 110 layer-1
   leaves = just the bridge deck), not a full second floor.
2. **Every cross-layer link joins two leaves at (essentially) the SAME (x,y)** — e.g. BarrowFields
   idx 523 (L0) ↔ idx 2255 (L1), both at (47.0, 57.0). This is the "stacked nodes at same x,y, different
   navLayer, explicitly linked" model — confirmed empirically, not just inferred.
3. **Layers connect only to ADJACENT layers** (0↔1, 1↔2; never 0↔2). Confirmed by the pair histogram.
4. Some levels ship `numLayers=2` with a **degenerate/empty** second layer (BanditCampBoss: 0 layer-1
   leaves, 0 cross-layer edges) — a vestigial layer slot.

**Answer to "is it truly 3-D?": no.** It is a stack of independent 2-D projections (one quad-tree per
layer, all in the same x,y plane) plus a small set of discrete transition edges. Height only exists in the
*geometry/collision* the layers were built from, never in the nav data.

## 2. How multi-layer nav is GENERATED (editor vs derivable)

The generator is `CNavQuadTree::Initialise(CNavigationAreaInit&)` (0x03290030). Its **input** — the
`CNavigationAreaInit` — is what decides how many layers exist and where transitions go. That input is built
by two `CWorldMap` functions, both decompiled this session:

### 2.1 `GetMapNavigationAreaInit` (0x01c905d0) — gathers obstacles, action points, and per-thing layer

1. Calls **`GetMapNavigationAreaUpdateInfo`** first (→ §2.2: per-layer blocking lines, switchable
   blockages, **transition points**, and the layer count).
2. `GetAllLeafThings<CThingBuilding>` and `<CThingObject>` in the map box → for each with a physics TC,
   `GetBoundingInfo(CTCPhysicsBase)` → push a `C2DBoxF` (the DetailedAreas / obstacle footprints).
3. `GetAllLeafThings<CThingVillage>`, `<CThingAICreature>`, `CTCCreatureGenerator`s, and
   **`CTCDNavigationSeed`** things → for each, compute its layer with
   **`GetNavigationLayerAt(thing.Pos3D)`** and push a `CNavigationPosition(pos2D, layer)` (action
   point / seed, tagged with the layer it sits on).

So obstacles come from **physics collision meshes**; seeds/action points are tagged with a layer via a
Z-aware lookup.

### 2.2 `GetMapNavigationAreaUpdateInfo` (0x01c8f390) — the walkability + line + transition source

Meaningful callees (decompiled) reveal every source:

- **`CMap::IsPassableAt(C2DCoordI)` / `CMap::IsPrefNavAt(C2DCoordI)`** — the **TopologyWeights** source =
  the LEV terrain walkable byte (+15) and preferred-path byte (+20). Confirms the pinned model in
  `NAVMESH_RE.md` (0xFF blocked / 0x00 preferred / 0x80 normal).
- Filter `CThingFilter_HasNavigationInformation` (bound with `OverlappingArea` + quest filter) → iterate
  things that **carry nav info**. For each: `HasPhysicsMeshObject` / `GetPhysicsMeshObject(CTCPhysicsBase)`
  → **`GetNoNavCollisionLineLists(CThingPhysical)`** — i.e. the **blocking lines are the 2-D outline of
  each thing's physics collision mesh**, bucketed per layer.
- `GFGetMapThingUIDFromThingUID` — the **switchable-blockage key** (door/gate UID low32), matching the
  proven switchKey model.
- `CStringParser` / `ReadAsInteger` — parses integer nav data off a thing (e.g. a transition/gate thing's
  layer indices) — this is where hand-placed transition hints enter.

### 2.3 `GetNavigationLayerAt` (0x024a35c0) — how a point's LAYER is decided

Not a raw Z-band. For a point it runs a `CThingFindNavigationLayerAt` visitor over all
**`HasNavigationInformation`** things whose bounding box overlaps the point (a 0.1-unit tolerance,
`0x3dcccccd`), and returns `CThingFindNavigationLayerAt::GetLayer()`. In other words: **the layer at (x,y,z)
is whatever the nav-info thing placed there declares.** Multi-level structure is therefore *authored by
placing nav-info things (buildings/floors/bridges/transition-gates) that carry a layer value*, and the
quad-tree builder then rasterises each layer's walkable area from terrain + collision.

### 2.4 So: auto-generated, but not from bare geometry

- The **quad-tree subdivision** of each layer is fully automatic (proven: `parse_navmesh.py regen`
  reproduces all 398 retail trees exactly).
- **Which layers exist, and the transition points between them, are supplied to the builder** by
  `GetMapNavigationAreaUpdateInfo` from nav-info things + their physics collision. They are *not* invented
  by the quad-tree code from overlapping triangles.
- **Editor trigger:** `CEditControlCentre::GenerateNavigationInformation` (0x0204b700) rebuilds nav for
  every map. This runs inside FableWin/ego_r with the live world loaded (things + collision available).

TNG evidence (retail corpus): the nav-hint thing types are **`NAVIGATION_SEED`** (`CTCDNavigationSeed`,
114 placements — island anchors, tagged per layer), **`TRANSITION_GATE`** (52 — nav-info gates),
**`NAVIGATION_ROUTE`** (35). Multi-layer interiors carry these (HeroGuildComplexInside, Bordello,
BarrowFields each have a TRANSITION_GATE + NAVIGATION_SEED). Note `OBJECT_REGION_TRANSITION_GATE` is a
*region-graph* portal, distinct from the nav-layer transition points (its position did not match the
cross-layer link in Bordello — the layer transition is derived from the mezzanine collision, not that gate).

## 3. Spiral Mountain viability verdict (honest)

**Can a climbable spiral be represented?** Partially, with a specific, unavoidable transformation:

- A continuous helical ramp **overlaps itself in x,y and has multiple valid Z per (x,y)**. The nav format
  stores no Z and represents each (x,y) region once per layer, so the spiral must be **sliced into discrete
  horizontal layers** — one per revolution (or per landing). Each slice is a flat 2-D annular patch on its
  own `navLayer`; adjacent slices are joined by a **transition point** where the ramp passes over itself.
- This is exactly how the retail engine does a **spiral/stacked staircase**: discrete floors + a transition
  at each landing. A 2–4 turn tower staircase is squarely within the retail envelope (HeroGuildComplexInside
  is a 3-layer building; HookCoast reaches 5 layers).

**Limits:**

- **Max layers:** retail ceiling observed = **5**. The `navLayer` byte is a `u8` so the format allows more,
  but nothing exercises >5; treat 5 as the safe practical cap and design the spiral with ≤5 stacked slices.
- **Transitions are DISCRETE, not continuous.** You cannot represent a smooth helix as one surface; you get
  N flat rings joined at N−1 seams. Pathfinding steps ring→ring at each seam (an ordinary neighbour edge).
  Visually the ramp can still be a continuous mesh; only the *nav* is quantised into rings. For creature
  AI this is fine (they path ring to ring and the animation follows the mesh).
- **Each layer's walkable area is carved from terrain + collision**, so every ring needs a real walkable
  surface under it — i.e. the spiral must exist as **physics collision**, not just a graphics mesh.
- **Same-(x,y) constraint on transitions:** a transition links two leaves that share an (x,y) footprint on
  adjacent layers. Place the ring seams where the upper ring is directly above the lower ring's end (the
  natural over-under point of a spiral) so a valid transition point exists.

**Verdict: VIABLE as a discrete N-ring stacked staircase/tower (N ≤ ~5), NOT as a single continuous helical
nav surface.** The current `MESH_FORGE_SPIRAL_MOUNTAIN` is graphics-only and thus non-walkable until it is
given per-ring collision + nav.

## 4. The realistic authoring path

### Route A — NATIVE (extend the hub's nav generator). **Recommended, medium effort.**

The hub already has `tools/parse_navmesh.py generate` — a byte-exact terrain-only **single-layer** writer,
validated across 148 nav LEVs. The on-disk multi-layer format is **fully known** (this doc + NAVMESH_RE.md).
What's missing is purely the *authoring* logic, not format RE:

1. **Per-layer rasters (format-trivial).** Emit `numLayers = N`; run the existing subdivision per layer over
   that layer's walkable raster. The writer already tags `navLayer`; today it hardcodes layer 0. Change:
   loop layers, set the byte, keep index/region/neighbour passes per layer. **Small.**
2. **Layer membership from the mesh (the real work).** Decide which x,y belongs to which ring. For a spiral
   this is deterministic: slice the mesh by height bands (one ring per revolution) and rasterise each band's
   top surface to a walkable grid (its own "TopologyWeights"). This is a **mesh→per-layer heightfield**
   step you write offline; you own the mesh, so you set the bands. **Medium.**
3. **Transition points (small, but must match runtime).** Emit a cross-layer neighbour pair at each ring
   seam: pick the (x,y) where ring k's exit sits under ring k+1's entry, make the two covering leaves mutual
   neighbours (exactly what `JoinNavigationLayers` would do). The generator already computes edge adjacency;
   add explicit cross-layer neighbour insertion at authored seam points. **Small.**
4. **Seeds/action points per layer.** Reuse the island-keep logic per layer; anchor each ring with a
   `NAVIGATION_SEED` so it isn't culled as an unreachable island (the existing rule already keys off seeds).

Scope: **format gap ≈ zero** (all four node kinds, numLayers, cross-layer neighbours are proven and
round-trip byte-exact). The engineering is (2) mesh-to-per-layer-heightfield slicing + (3) authored seam
placement. Estimate: a focused extension of `parse_navmesh.py generate` (a `generate --layers` mode driven
by a small ring-band spec). This is the path consistent with the **own-the-pipeline** philosophy (MEMORY):
FableForge writes the nav natively; no editor dependency.

Caveats the generator must respect (all documented): switchable leaves never merge; neighbour-list *order*
isn't reproduced (semantically a set — fine); depth cap level 5 (no DetailedAreas) is fine for a ring.

### Route B — EDITOR (place the mesh in ego_r/FableWin and let it build nav). **Not realistic here.**

`GenerateNavigationInformation` would build multi-layer nav *only if*:
- the spiral is present as a **physics collision mesh** (a `[PHYSICS]` tagged BBM, per
  `BIG_MESH_*`/def collision-mesh fields), not just the graphics prim we baked, **and**
- per-ring **nav-info things** are placed so `GetNavigationLayerAt` returns the right layer over each ring,
  **and** transition-gate/route hints exist at the seams.

That is the *same* authoring problem as Route A (slice into rings, declare layers, mark seams) but performed
through a Lionhead editor we do not drive headlessly and whose collision-import path for arbitrary imported
meshes is unproven. `GetNoNavCollisionLineLists` shows the editor only knows a thing's collision from its
**physics mesh object** — an imported graphics mesh with no physics mesh contributes nothing to nav.
**So the editor will not auto-generate walkable nav for a bare imported mesh; it needs the same per-ring
collision + hints you'd build for Route A.** Given we already own the LEV nav writer, Route A is strictly
less work and fully offline.
